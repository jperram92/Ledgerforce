# T-0104 — API skeleton: NestJS on SWC, health check, per-request tenant transaction

## Goal
`apps/api` exists as a NestJS 12 app built with SWC (decorator metadata) and tested with Vitest
plus `unplugin-swc`. It has `GET /health` (DB reachable as `lf_app`) and a request-scoped tenant
transaction. Every request that touches tenant data runs inside `withTenant` (T-0010), using the
tenant from a `TenantResolver`. Until authentication exists (T-0011), the production resolver
refuses every request with 401; there is no header-based tenant selection.

## Context (design refs)
- Design §7.1 (NestJS), §6.7 (tenant isolation), §3.9 (commands); ADR-0002; RQ-0013; RQ-0015.
- Split out of T-0011 on 2026-10-24 by claude (RQ-0015 finding 3: NestJS cannot run on Node
  type stripping, so the API needs its own build/test toolchain; T-0011 would exceed one session).
- apps/api/AGENTS.md local rules apply (lf_app only, money as decimal strings, no ledger writes).

## Open questions (→ research before start)
- [x] Toolchain for decorators: SWC + unplugin-swc (RQ-0015).

## Acceptance criteria (each maps to a test + SS id)
- [x] **SS-PLAT-28** (db-integration) — Every API request runs in its own tenant transaction.
  *Given* tenants A and B, each with a company; *when* a request resolved to A lists companies;
  *then* only A's company is returned. A request with no resolvable tenant gets 401 and runs no
  SQL. After the request, the pooled connection carries no tenant context. `/health` returns 200
  `{"status":"ok","db":"ok"}` without any tenant.

## Expected results defined before build
- `apps/api/src/tenancy/tenant-transaction.db.test.ts`: tests named `SS-PLAT-28: …` covering A sees only A, no tenant → 401, pool clean after request.
- `apps/api/src/health/health.db.test.ts`: 200 and body shape.
- `apps/api/src/di.test.ts`: a provider injected only by constructor type resolves (proves decorator metadata works under Vitest 4 + SWC; RQ-0015 follow-up).
