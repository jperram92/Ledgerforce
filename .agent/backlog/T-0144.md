# T-0144 — CSRF guard for cookie-authenticated mutations (split from T-0097)

## Goal
Supersedes T-0097 (part). Browser-session (`lf_session` cookie) requests with an unsafe method are
accepted only from the LedgerForce origin: `Sec-Fetch-Site: same-origin`, or, without Fetch
Metadata, an `Origin` equal to `LF_PUBLIC_URL`'s origin (OWASP CSRF cheat sheet, RQ-0141 F6–F8).
Bearer API-token requests carry no ambient credential and are unaffected. Design §6.9.

## Acceptance criteria (each maps to a test)
- AC-1 Cookie-authenticated POST with `Sec-Fetch-Site: cross-site` or `same-site` → 403
  `{error:'csrf_rejected'}`, no handler runs → `apps/api/src/security/csrf.db.test.ts`
- AC-2 Cookie-authenticated POST with no Fetch Metadata and a foreign or `null` Origin → 403; with
  the public origin → allowed → same file
- AC-3 Cookie-authenticated POST with neither header → decision per the ADR (OWASP recommends
  fail-safe reject); Bearer-token POST without headers → allowed → same file
- AC-4 Existing session-based DB tests send `Sec-Fetch-Site: same-origin` through their shared
  helpers (about 25 files under `apps/api/src/**`), no assertion weakened

## Open questions
- Fail-safe (reject cookie mutations lacking both headers) vs fail-open: OWASP recommends
  fail-safe; it changes every session-based test helper → decide in a security ADR (human gate).
