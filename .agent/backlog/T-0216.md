# T-0216 — Bills mailbox: settings API/UI and OAuth2 XOAUTH2

## Goal
Let an administrator connect the company's bills mailbox (T-0127 stores and polls it) from
Settings, and support OAuth2 `AUTHENTICATE XOAUTH2` so Microsoft 365 (no IMAP passwords since
2022, RQ-0177 F3) and Google Workspace mailboxes work. Split from T-0127 (DL-0810).

## Scope change (2026-11-23, DL-0930)
Split: this card builds the OAuth slice end to end (research, ADR-0105, migration, XOAUTH2,
token exchange and refresh, sealed refresh token with rotation, poller, connect API). The
password-mailbox settings API, "Test connection", inbound-address display/rotation and the
Settings screen (old AC-1, AC-2, AC-4) moved to **T-0237**; unattended grants (Microsoft
app-only, Google service account) to **T-0238**. Old AC-3 is kept and extended below.

## Acceptance criteria (current)
- [x] AC-A (unit) PKCE S256 per RFC 7636 vector; authorization URL per provider (scopes, PKCE,
  state, login_hint, offline access); code exchange and refresh against recorded token
  responses; `invalid_grant` → auth_failed, transport/5xx/oversize → connect_failed; no secret
  in any error → `packages/modules/ap/src/mailbox-oauth.test.ts` (SS-PLAT-189)
- [x] AC-B (unit) `AUTHENTICATE XOAUTH2` with SASL-IR: initial response equals Google's
  published vector; the fake server accepts the right token; a JSON challenge is answered with
  an empty line and maps to auth_failed → `packages/modules/ap/src/imap-client.test.ts`
  (SS-PLAT-190; this is old AC-3)
- [x] AC-C (db) an OAuth mailbox (refresh token sealed, AAD field `refresh_token`) polls through
  a recorded refresh; a rotated refresh token is re-sealed in place; invalid_grant is recorded
  as auth_failed; the database refuses secret updates on password rows → 
  `packages/modules/ap/src/inbox-mailbox-oauth.db.test.ts` (SS-PLAT-191)
- [x] AC-D (api-db) start needs settings.setup.manage + step-up + Idempotency-Key and returns a
  PKCE authorization URL; the callback is bound to the same user and session, single use and
  expires after 10 minutes; it connects the mailbox, supersedes the old one, returns no secret,
  and writes audit rows → `apps/api/src/ap/bills-mailbox-oauth.db.test.ts` (SS-PLAT-192)

## Acceptance criteria (original, superseded by the scope change above)
- AC-1 An administrator saves host/port/username/folder/password; the response and every read
  return no secret; a change supersedes the active row → `apps/api/src/ap/bills-mailbox.db.test.ts`
- AC-2 "Test connection" reports the fixed error class (ADR-0095) against the fake IMAP server
  → same file
- AC-3 XOAUTH2: with a token from a recorded client-credentials (or refresh-token) exchange the
  client authenticates against the fake server; the OAuth secret is sealed like the password
  → `packages/modules/ap/src/imap-client.test.ts`
- AC-4 Settings screen with Playwright evidence (SS ids from the PLAT family)

## Open questions
- Microsoft 365 app-only IMAP (client credentials + Exchange application RBAC) vs delegated
  refresh token: sources disagree (RQ-0177 S7) — new RQ against current Microsoft docs.
- Permission for the setting (bank-detail-like SoD? mailbox credentials are not payment data).
