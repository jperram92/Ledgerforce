# T-0217 — A Stripe refund that fails after it was recorded paid

## Goal
Security review r10, finding I1. A refund that LedgerForce sent or adopted while it was `pending`
can later become `failed` or `canceled` at Stripe. The money then goes back to the merchant's
balance, but LedgerForce's refund document stays `paid`. The books overstate the refund: the
customer's credit is cleared and Stripe clearing is credited. A resend needs `requested`, so
nothing can follow.

Handle Stripe's `refund.updated` / `charge.refund.updated` webhook, which is signature-verified
and replay-protected like the existing webhook:
- record the new status on `app.stripe_refund`;
- for `failed` or `canceled`, reverse the GP-006 Stripe-variant entry through the posting engine
  (posted is immutable, so the correction is a reversal), which reopens the customer's credit;
- open a Sync issue that names the refund document.

## Acceptance criteria
- [ ] AC-1 (research) an RQ on the webhook event shapes (stripe SDK types) and on how comparable
      systems book a failed refund; a golden posting for the reversal if one is needed
      (DL-0263 delegation)
- [ ] AC-2 (contract, db) a `refund.updated` to `failed` for a recorded refund reverses its entry
      once and reopens the credit; a replayed event does nothing
- [ ] AC-3 (db) the document's history shows the failure, and a new refund for the reopened
      credit is possible under the normal approval
