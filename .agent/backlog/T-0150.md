# T-0150 — Payment batch API routes and batch cancellation

## Goal
Expose the T-0054 payment-batch workflow over the API and add the missing cancel path, so the
release screen (T-0087) and the ABA export (T-0056) have routes to call.

## Context (design refs)
- Design §6.2 (step-up), §6.4, §6.5 rule 1, §6.8; UC-06 A1/A2/A3; ADR-0025, ADR-0026.
- Found during T-0054 (DL-0350…DL-0354). The module functions are `listPayableBills`,
  `createPaymentBatch`, `releasePaymentBatch`, `getPaymentBatch` in
  `packages/modules/ap/src/payment-batches.ts`; the database function
  `app.payment_batch_release` repeats every release check (migration 0042).

## Open questions (→ research before start)
- Cancellation of a created / partially released batch: who may cancel (creator, any releaser,
  Finance Admin?) and whether cancelling needs step-up. Not stated in design §6.5; decide by
  DL, or escalate as a security decision if it changes the control model.

## Acceptance criteria
- [ ] Routes: GET /payment-batches/proposal, POST /payment-batches, POST /payment-batches/:id/release
      (`ap.payment_batch.release`, step-up via the interceptor → 401/403 `step_up_required`;
      SoD refusal 403 `{error:'sod_violation', rule}` with the denial audit committed),
      GET /payment-batches/:id. The `sessionId` passed to the module is the request's session.
- [ ] Cancel: a SECURITY DEFINER function moves created / partially_released → cancelled and
      the payments → cancelled, so their bills can be proposed again; audited.
- [ ] api-db tests for every route, cross-tenant coverage unchanged.
