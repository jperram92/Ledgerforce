## Report (round 7, claude, 2026-10-26)

**Built**
- RQ-0040 (resolved): sObject Collections upsert/update contract, `allOrNone`, ≤ 200 records,
  per-record results in a `200`, API 67.0 (≥ 46.0), 401/403 `REQUEST_LIMIT_EXCEEDED`/429/503,
  `Retry-After` (not documented for Platform REST), `Sforce-Limit-Info`. developer.salesforce.com
  was unreachable (proxy 403), so the facts come from WebSearch extracts, as in RQ-0024 and RQ-0036.
- `packages/connectors/salesforce/src/writeback/`:
  - `mapping.ts`: the `writeBack` v1 payload contract, plus `FIELD_MAP` and the status tables (all data).
  - `batch.ts`: ≤ 200 records per request, upserts before updates, dedupe and merge, exact
    money literals.
  - `collections.ts`: REST client, error classification, Retry-After, `ApiUsageGate` at 25 %.
  - `writeback.ts`: `writeBack` and the outbox handler `salesforce.writeback`, which takes its
    token from the T-0063 connection store and re-signs once on a 401.
- Test-only `@ledgerforce/connector-salesforce/testing`: a fake sObject Collections server that
  validates against `salesforce/force-app` metadata, and a documented fixture.
- ADR-0036 (Proposed, integration, no human gate); DL-0190..0194. No migration (0029 unused).

**Proven**
- SS-UC03-04, SS-UC04-02, SS-PLAT-83, SS-PLAT-84: `writeback.payload.contract.test.ts`, 12 tests.
- SS-UC01-09: `apps/worker/src/salesforce-writeback.outage.db.test.ts`, 4 tests. During the 503:
  the journal is committed, the job is in `retry`, there is no inbox row, and it stays queued
  across a second attempt. On recovery: exactly one upsert, then completed. Also proven there:
  a redelivery is skipped, an expired token is re-signed once, and a company with no connection
  is a no-op.

**Open questions / follow-ups (no human gate needed)**
- Sync issues inbox for dead-lettered write-backs (design §5.6 rule 2): with 10 retries the
  backoff gives up after about 14.5 h, so a longer outage dead-letters until the one-click retry
  or the nightly reconciliation catches up.
- Conflict logging when a user edits a LedgerForce-owned field in Salesforce (design §5.5) needs
  the inbound CDC comparison. Not built.
- Out-of-order snapshots across jobs can briefly leave an older value in Salesforce
  (ADR-0036 trade-off).
- The HTTP calls run inside the delivery transaction while the connection row is locked, so
  write-backs of one company are serialised (accepted for MVP volumes).
- The worker entrypoint does not register `salesforceWriteBackHandler` yet: apps/worker has no
  boot module. Wire it in when the worker gets its runtime config (kms, http clients).
