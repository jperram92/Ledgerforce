# T-0136 — Bills inbox: HTTP routes and screen (split from T-0086, DL-0442)

## Goal
The AP Clerk sees bills that suppliers emailed in (T-0051 `app.bill_inbox_item`), opens the PDF,
and codes an item into a draft bill on the T-0086 entry form; the draft then follows the T-0086
approval screens.

## Context
- `packages/modules/ap/src/inbox.ts`: `ingestBillEmail`, `codeInboxItem` exist; no API routes.
- T-0086 screens: `apps/web/src/purchases/` (BillFormPage takes the coding choices from
  `GET /ap/bill-coding`).

## Open questions (→ research before start)
- How the PDF is served (content-disposition, CSP for an inline viewer vs download only) — a
  security-relevant choice; open an RQ.

## Acceptance criteria
- [ ] AC-1 (api-db): `GET /ap/inbox?company_id=` lists items (status, sender, subject, suggested supplier, attachments) under `ap.read`; `GET /ap/inbox/:id/attachments/:n` returns the PDF; `POST /ap/inbox/:id/code` (ap.bill.enter, client-chosen bill id, idempotent) calls `codeInboxItem` and records SoD `bill.enter`.
- [ ] AC-2 (e2e-playwright, screenshots): an inbox item becomes a draft bill from the UI and appears on `/purchases/bills`; register a new SS id under UC-05.

## Steps
- [ ] 1. RQ for serving PDFs; failing tests first (`tdd-cycle`)
- [ ] 2. API routes
- [ ] 3. Inbox screen + e2e + evidence
- [ ] 4. verify, cross-review, finish
