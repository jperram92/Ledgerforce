# T-0123 — Tax determination part 2: resolver and confirmations

## Goal
Replace the tax-code step of the T-0039 resolver with **ADR-0044 R4–R6 and R9**. The precedence
is:
1. explicit line code, i.e. one a user entered on the line (codes copied from Salesforce,
   templates or defaults are not explicit), with an override reason when it differs **or when no
   code was determined**, and for EXP/EXS also the R4 confirmation;
2. product-inherent class (GST_FREE_INHERENT → FRE, INPUT_TAXED → INP, BAS_EXCLUDED → N-T);
3. the `app.tax_determination` cell (code / confirm → code or alt / manual → `TAX_CODE_REQUIRED`);
4. no cell → `NO_TAX_RULE`; an unclassified party or product → `NO_TAX_CLASS`.

A party default alone never yields a GST-free or export code (on sales, nor an input-taxed or
BAS-excluded code). Confirmations for `confirm` cells are stored on the document line with key,
user, time, evidence reference, the determination row id and the condition text, append-only and
frozen at posting. Every resolved line stores its resolution trace. Credit notes, adjustment notes
and reversals take the original line's code, confirmation and trace (ADR-0044 R4/R5 as accepted,
wording W3, W5, W6, W9).

This supersedes rule (3) of DL-0260 (the single/equal default and `TAX_CODE_CONFLICT`). The T-0039
tests for that behaviour are **superseded, not deleted**: they are rewritten as `NO_TAX_RULE` and
matrix cases, and the old test names stay in a comment or a superseded `describe` that asserts the
new behaviour (ADR-0014). Never `.skip`.

**Human gate.** Met: ADR-0044 was accepted on 2026-11-08 under DL-0282 after persona re-review
DL-0285 (DL-0286). Build against the accepted text.

## Acceptance criteria (each maps to a test + SS id)
- [ ] **SS-PLAT-132** (unit) Precedence R5 and every refusal is named: `NO_TAX_RULE` (direction,
  party class, product class, date), `NO_TAX_CLASS` (which side), `TAX_CODE_REQUIRED` (manual
  cell), `TAX_OVERRIDE_REASON_REQUIRED`, `TAX_CONFIRMATION_REQUIRED`. Product-inherent classes win
  over any party class. A `confirm` cell returns `alt_tax_code` without a stored confirmation and
  `tax_code` with one. Also, each as its own case:
  - an explicit code on a line where steps 2–4 produce **no** code (`manual` cell, `NO_TAX_RULE`,
    `NO_TAX_CLASS`) without a reason → `TAX_OVERRIDE_REASON_REQUIRED` (W3);
  - an explicit `EXP` or `EXS` with a reason but no R4 confirmation for `s38-185`/`s38-190` →
    `TAX_CONFIRMATION_REQUIRED` (W3);
  - a code copied from a Salesforce field (`LF_Tax_Code__c`), a template or a party/product
    default is not treated as explicit (it never bypasses steps 2–4);
  - the returned code must be valid on the document tax date (invoice date, supplier bill date, or
    receipt date of an uninvoiced receipt), else `NO_TAX_RULE` (W6).
  → `packages/modules/products/src/tax-determination.test.ts`
- [ ] **SS-PLAT-133** (unit, fast-check) R9 invariant: no resolution returns FRE/EXP/EXS (any
  `gst_free` kind) unless the product is GST_FREE_INHERENT, a matched confirm cell has a stored
  confirmation, an explicit line code has an override reason (required when it differs or no code
  was determined) and, for EXP/EXS, an R4 confirmation, or it is the purchase-side
  DOMESTIC_UNREGISTERED cell. On direction `sale` the same holds for codes of kind `input_taxed`
  and `bas_excluded` (with (a) read as INPUT_TAXED / BAS_EXCLUDED). The generator produces
  **arbitrary matrices that satisfy the R3 guard** (any classes, `*` on either column, any
  outcomes, overlapping rows resolved by the W1 specificity order), not only the R7 seed (W9). →
  `packages/modules/products/src/tax-determination.prop.test.ts`
- [ ] **AC-3** (db-integration) The line confirmation record (R4) is stored in the tenant's
  transaction, is RLS-covered, and records `confirmed_by`/`confirmed_at`/evidence ref, the
  `app.tax_determination` row id and the condition text as confirmed. An unconfirmed line records
  the alt code it fell back to. The record is append-only: it can be added or withdrawn (as a new
  row) while the document is a draft; after the document posts, insert/withdraw for that line is
  refused and UPDATE/DELETE are refused at any time. Confirming requires a distinct permission
  (`tax.confirmation.record` or the RBAC name chosen at claim, logged); a caller without it is
  refused. → `packages/modules/products/src/tax-determination.db.test.ts`
- [ ] **SS-PLAT-135 / AC-5** (db-integration) Resolution trace and adjustments (W5, W6):
  - every resolved document line stores its trace: deciding step (explicit, product-inherent, cell,
    refusal), the `app.tax_determination` row id if any, the party and product tax classes used and
    the tax date;
  - a change to a party's or product's `tax_class` writes an audit-log row (old value, new value,
    user, time);
  - a credit note, adjustment note or reversal line copies the tax code, confirmation and trace of
    the line it adjusts and does not re-resolve, even after the matrix cell or the classes changed
    (test: export invoice EXP with confirmation → new cell row / reclassify the party → credit note
    line is still EXP);
  - a posted line is never re-resolved; a draft is re-resolved at posting, and a changed result is
    returned to the caller as a "changed since draft" result before posting.
  → `packages/modules/products/src/tax-determination.db.test.ts`
- [ ] **AC-4** (unit) The former T-0039 TAX_CODE_CONFLICT cases now resolve through the matrix or
  refuse `NO_TAX_RULE`. In particular, OVERSEAS/NON_RESIDENT_OFFSHORE × TAXABLE_SERVICE without a
  confirmation → GST (alt). → `packages/modules/products/src/matrix.resolve.test.ts`
