# T-0140 — Bill API routes and a shared SoD store

## Goal
Expose the T-0052 bill workflow over the API (RBAC `ap.bill.enter` / `ap.bill.approve`, audit
row per mutation, `sod_exception` body as in ADR-0026) and remove the duplicated SoD readers:
`currentSodSettings` / eligible-approver count exist both in `apps/api/src/sod/sod.service.ts`
and `packages/modules/ap/src/bill-approval.ts` (DL-0332).

## Context (design refs)
- Design §6.4, §6.5 rule 3, §6.8; UC-05; ADR-0026; RQ-0116 F6 (refusal returned, not thrown).
- Found during T-0052 (DL-0332, DL-0333). The UI (T-0086) needs these routes.

## Open questions (→ research before start)
- Where the shared SoD store lives (a `@ledgerforce/shared` subpath cannot import Kysely types
  from `@ledgerforce/db`; candidate: `@ledgerforce/db/sod`). Decide by RQ/DL.

## Acceptance criteria
- [ ] Routes: POST /bills/:id/submit, /approve, /reject, /return-to-draft, GET /bills/approval-queue; a SoD refusal answers 403 `{error:'sod_violation', rule}` and stays audited (the denial audit row must commit although the request fails).
- [ ] One implementation of settings / history / eligibility used by `checkSod` and `approveBill`; the API and module db tests stay green unchanged.
- [ ] Line removal on a draft bill (lines are never deleted: decide supersede-by-flag vs. re-entry) — research first.

## Steps
- [ ] 1. Research gate (shared store location, line removal)
- [ ] 2. Failing api-db tests
- [ ] 3. Implement
- [ ] 4. verify, cross-review, register
