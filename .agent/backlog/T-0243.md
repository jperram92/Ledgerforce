# T-0243 — Bills mailbox OAuth2 hardening: code exchange outside the DB transaction, rotation failure handling, verifier cleanup, rotation-function tests

## Goal
Security review r12 of T-0216 (DL-0899) passed with one medium and three low findings.
- M1: the callback exchanges the code with the provider (up to 15 s) inside the request's database transaction, holding a pooled lf_app connection and a row lock; this breaks the module's "no network I/O inside a transaction" rule.
- L1: if re-sealing a rotated refresh token fails (DB or KMS error) the new token is dropped and the old one kept.
- L2: the PKCE verifier is stored in plain text and never deleted.
- L3: no test checks the rotation function's owner, SECURITY DEFINER flag or search_path.

## Acceptance criteria
- [x] AC-1 (api-db) the callback consumes the request in one transaction, exchanges the code outside any transaction, then saves and audits in a second; a slow provider holds no DB connection
- [x] AC-2 (db) a failed re-seal of a rotated refresh token is retried or surfaced as a named mailbox status; the mailbox is never left with a token the provider has revoked without an operator-visible error
- [x] AC-3 (db) the PKCE verifier is cleared (or sealed) once the request is consumed or expired
- [x] AC-4 (db) tests assert the rotation function's owner, SECURITY DEFINER and pinned search_path
