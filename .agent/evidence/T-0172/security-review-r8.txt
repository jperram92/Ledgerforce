### T-0180 findings
- **L1 (low) — re-activation re-prints a designated account.** remittance.ts:43 filters `status = 'active'`, and lf_app may UPDATE bank_account.status. An account archived while designated, then re-activated, prints again without a new approval. Same approved account, so low. Fix: on archive, clear designation via an approved removal, or have the guard refuse re-activation of a designated account without a change record (or document as accepted).
- **L2 (low) — small-team self-approval has no extra compensating control specific to payment redirection.** Only the generic sod_exception record. Suggest notifying all Owners/Finance Admins (email) on any remittance account change, approved or self-approved (design §1 principle 5, §6.5).
- **L3 (info) — ADR-0080 is category api, human_gate no**, but it fixes the SoD rule and DB guards. Acceptable because it only implements owner-accepted ADR-0079; noted for the owner.

### T-0172 findings (ranked)
- **F1 (medium) — Stripe is called inside the API request transaction before the ledger posting; a later failure leaves money refunded with no books, and a lost commit can lead to a second refund after 24 h.**
  - (a) refund.ts:277-336: createRefund runs, then post()/allocate()/insert. If post() fails (e.g. period locked/closed, account inactive — a PostingError), isTransient (refund.ts:374-376) classifies it as transient: the savepoint rolls back the posting but Stripe has already refunded. The worker retries with the same key (Stripe returns the same refund) and fails again until KEY_EXPIRED / dead letter. Money is out, AR not reduced, and the Sync issue does not say Stripe already refunded.
  - (b) controller.ts:284-293: after a successful send and RELEASE SAVEPOINT, the outer transaction can still fail to commit (deferred constraint, audit insert, connection loss). Approval, outbox event and posting all roll back; Stripe refund stands; the refund is "requested/unapproved" again. A re-approval within 24 h replays at Stripe (same key, if params same); after 24 h a re-approval gets a fresh approved_at, passes the 23 h check and sends a **second** refund.
  - Fix: run every check that can refuse the posting (period open, accounts postable — e.g. the engine's preview/validate) *before* calling Stripe; classify PostingError as non-retryable with a code that says "sent to Stripe, not posted"; before createRefund on any send, look up existing Stripe refunds for the payment_intent with metadata lf_refund_id (Stripe List Refunds by payment_intent) and adopt one if found; or move the send out of the request transaction (worker-only after commit, keeping the approve route's response as "pending").
- **F2 (low, latent) — step-up condition metadata inherits independently of max age.** permission.decorator.ts:44-52, stepUpWhenOf uses meta() falling back to class. A class-level `@RequireStepUp(n, cond)` plus a handler-level unconditional `@RequireStepUp(m)` makes the handler conditional too. No current usage. Fix: store `{maxAge, when}` as one metadata value so handler declarations replace both; add a unit test.
- **F3 (low) — TOCTOU between condition and handler reads (READ COMMITTED).** stripeRefundOnly returns false when the refund does not exist yet; if the maker's PUT commits between the condition's SELECT and getCustomerRefund (controller :250), the Stripe approval proceeds without step-up. Needs a pre-known client id and precise timing; the approver still needs permission and SoD. Fix: in the handler, when current.method === 'stripe', re-check that the condition was evaluated as true (e.g. interceptor sets a request flag, or the condition SELECTs FOR SHARE and the handler refuses a Stripe refund if the flag says "not required").
- **F4 (human gate) — ADR-0083 is category security, `human_gate: yes`, Accepted by claude "under DL-0477" via DL-0562.** DL-0477 delegated the listed items; item 3 says only "A Stripe refund is sent only after approval". Adding step-up is a strengthening and consistent with item 5, but the new conditional step-up mechanism in the central interceptor is a change to the authorization framework. AGENTS.md §6 keeps security ADRs with the owner. Ask the owner to confirm ADR-0083 (including the conditional step-up mechanism) is covered by DL-0477.
- **F5 (info) — worker-path posting has no createdBy** (refund.ts:437-446): the journal entry from a retried send is not attributed to the approver. Pass approvedBy from customer_refund_approval into the handler's send.
- **F6 (info) — tenant UUID sent to Stripe as metadata** (refund.ts:283). Acceptable (an opaque id), noted for the privacy register.
