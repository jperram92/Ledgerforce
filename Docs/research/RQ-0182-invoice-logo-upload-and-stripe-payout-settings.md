# RQ-0182 — Invoice logo upload and Stripe payout settings

## Question

T-0195 puts three optional step-8 settings on the Numbering and billing screen (RQ-0167 Q4):
the invoice logo, the accent colour and the Stripe payout settings. Open points:

- Q1. Logo transport: multipart/form-data or base64 in JSON? Which body limit, given Nest's
  100 kB JSON parser?
- Q2. Validation: what must be checked beyond the 512 KiB limit and the magic bytes that
  `setInvoiceSettings` already checks? Should metadata be stripped or the image re-encoded?
- Q3. SVG: allow it if sanitised?
- Q4. How is the saved logo shown back safely (preview on the screen)?
- Q5. Stripe payout settings: which accounts and parties may be the fee account, the payout
  account and the Stripe party, and can a saved value be cleared?
- Q6. Idempotency, audit and permission of the new writes.

## Why it matters

A logo is a user-supplied file that is stored, served back to the browser and embedded into every
invoice sent to customers (T-0165 renders it as a data URI into the PDF). An upload is the
classic route for stored XSS, parser exploits, decompression bombs and accidental disclosure of
personal data (camera Exif, GPS). The payout settings decide which accounts GP-027 posts to; a
wrong account posts real money to the wrong place.

## Findings

1. **Q1 transport.** Both work. Base64 in JSON costs 4/3 of the bytes (512 KiB → 683 KiB) but
   fits the repository's existing, reviewed pattern (S6) and Odoo's (S5); it needs no multipart
   parser (multer is only transitively present through `@nestjs/platform-express`, and using it
   directly would be a new runtime dependency, design §10.6). The 100 kB default parser cannot
   carry it, so a route-scoped reader like ADR-0078's is needed with a limit just above the
   largest valid body: 1 MiB (683 KiB of base64 plus the JSON keys). Larger bodies are 413 before
   the controller runs.
2. **Q2 validation.** Magic bytes alone accept a file that starts like a PNG and continues as
   anything (a polyglot, S1). A structural walk is cheap and needs no image decoder: for PNG
   check the signature, every chunk's length and CRC-32 (`zlib.crc32`, Node ≥ 22.2), IHDR first,
   IEND last with nothing after it; for JPEG check SOI, the marker segments and their lengths up
   to SOS, a SOF before SOS, and EOI at the end. Both give the image's width and height, so
   absurd dimensions (decompression bombs aimed at the PDF renderer) can be refused: a logo
   needs at most 4,000 × 4,000 pixels. Re-encoding (S1's first choice) needs an image codec
   (sharp/libvips or ImageMagick: new native runtime dependencies with their own CVE history,
   S1 "the image processor itself handles untrusted input"). Dropping metadata is possible
   without decoding: in PNG, ancillary chunks are designed to be droppable (S2), so keep only an
   allowlist of chunks that affect how the picture looks (IHDR PLTE IDAT IEND tRNS cHRM gAMA iCCP
   sBIT sRGB cICP bKGD pHYs) and drop text, Exif, time and unknown/private chunks (the CRC of a
   kept chunk does not change). In JPEG, drop APP1 (Exif/XMP), APP3–APP13, APP15 and COM before
   SOS; keep APP0, APP2 (ICC) and APP14 (Adobe) (S3). This removes GPS positions, camera serials,
   author names and embedded thumbnails from a file that will go to every customer.
3. **Q3 SVG.** Refuse. An SVG is a document, not a picture: script, event handlers, external
   references and XXE (S1, S12). The invoice renderer and the database CHECK accept only PNG and
   JPEG (S7); allowing SVG would need a maintained XML sanitiser (new dependency, bypass history,
   S12) and a change to the Approved rendering path. WordPress, by default, does the same (S12).
   The screen says to export the logo as PNG.
4. **Q4 serving.** Serve the saved logo from a dedicated read route behind `settings.read`, never
   from a public URL: the stored content type (PNG/JPEG only, magic bytes re-checked), a fixed
   generated file name (`invoice-logo.png|jpg`, S1), `Content-Disposition: inline`, the global
   `nosniff` and `no-store` (S8), and a `Content-Security-Policy: default-src 'none'; sandbox`
   (S4) plus `Cross-Origin-Resource-Policy: same-origin`, so the bytes can never run as a page.
   The web app shows it with `<img>` from the same origin (`img-src 'self'`); a file chosen but
   not yet saved is previewed from a `data:` URL (also allowed), never a `blob:` URL (the nginx
   CSP does not allow `blob:`).
5. **Q5 payout settings.** By GP-027's journal (S9) and design §3.2 (S11):
   - fee account: the company's active, postable, non-control **expense** account (debit normal);
   - payout account: the GL account of one of the company's **active bank accounts** in the
     company's base currency (payouts land in a bank account; the bank statement is reconciled
     against it), itself active, postable and not a control account;
   - Stripe party: an active party of the company with an active **supplier** role (Stripe
     invoices its fees).
   The connector never clears a payout field (S9) and payouts refuse while any is missing, so,
   like the brand colour, a saved payout field can be changed but not cleared. Each field is
   optional on the request; a field that is sent must be valid (422 with a plain reason) and is
   checked before writing (a foreign-key error would abort the request transaction).
6. **Q6.** As ADR-0085: `settings.setup.manage`, Idempotency-Key required (not stored),
   replay-safe by state (the same logo again — compared by SHA-256 of the cleaned bytes — or the
   same accounts again answer `changed:false` and write no audit row), one audit row per change.
   The audit row records the logo's content type, size and SHA-256, never the bytes.

## Conclusion / decision

1. `PUT /setup/billing/logo` with JSON `{company_id, logo: {content_type, content_base64} | null}`
   and a route-scoped JSON reader limited to 1 MiB; strict base64; the API cleans the file
   (`cleanInvoiceLogo` in `@ledgerforce/ar`: structural check, ≤ 4,000 × 4,000 px, metadata
   chunks/segments dropped) and then saves it through `setInvoiceSettings` (which keeps its own
   magic-byte and 512 KiB checks). 400 `INVALID_INVOICE_SETTINGS` in plain words; 413 above the
   body limit.
2. `GET /setup/billing/logo?company_id=` (settings.read) serves the bytes with the headers of
   finding 4; 404 `LOGO_NOT_SET` when none.
3. No SVG; no re-encoding (no image codec dependency); metadata is dropped without decoding.
4. `PUT /setup/billing/invoice` already accepts `brand_accent_colour`; the screen sends it.
5. `PUT /setup/billing/stripe` accepts optional `fee_account_id`, `payout_account_id`,
   `stripe_party_id`; `GET /setup/billing` lists `fee_accounts`, `payout_accounts` and
   `stripe_parties` and returns all four Stripe fields. Recorded in ADR-0100 (extends ADR-0085).

## Confidence

`high` for Q1, Q4, Q5, Q6 (repository code, Approved GP-027, fetched OWASP and comparable-system
evidence). `medium-high` for Q2 and Q3: the PNG/JPEG structures are stable published standards
and are exercised by unit tests on real encoder output; S3 and S12 were not re-fetched this
session. Known limit: segments after the first JPEG SOS (progressive scans) are kept verbatim;
APPn segments there are rare and cannot run as code (served as `image/jpeg`, `nosniff`, sandboxed).
Exif orientation is dropped with Exif: a phone photo used as a logo may show unrotated; logos are
normally exported from design tools without it.
