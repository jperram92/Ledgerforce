# ADR-0037: Self-hosted install — owner bootstrap, realm MFA, secrets and origin

## Status

Proposed — security category, waiting for product-owner acceptance. T-0094 is built to this
proposal so it can be judged on working, tested code (SS-PLAT-23, SS-PLAT-85, SS-PLAT-86).
Research: [RQ-0041](../research/RQ-0041-self-hosted-compose-install.md). Builds on ADR-0016 (OIDC
login and sessions), ADR-0025 (MFA and step-up), ADR-0027 (user lifecycle) and ADR-0029 (job
queue privileges) without changing them.

## Context and problem statement

Design §6.3: "a single `docker compose up` … creates the database, runs migrations, seeds templates
and prints a one-time owner setup link; no default passwords exist." LedgerForce has no JIT
accounts: a user must be invited with the IdP's `(issuer, subject)` before the first login
(ADR-0016, ADR-0027), and the Owner must sign in with MFA (design §6.2). Keycloak's admin API
cannot return an action link without sending e-mail (RQ-0041 finding 4), and a fresh install has
no SMTP.

## Decision drivers

- No default or shared credential anywhere; every secret unique per install and never committed.
- Reuse the existing invite model and MFA rule instead of adding a second login path.
- Least privilege: lf_app at runtime, lf_migrator only in the one-shot setup, each secret only in
  the containers that need it; the IdP's admin surface not public.
- Works on one VM without SMTP, and is provable end to end in CI.

## Considered options

1. SMTP + mail catcher so Keycloak e-mails the action link — a fake mailbox in production.
2. A third-party Keycloak provider that returns the action link — a new runtime dependency inside
   the IdP.
3. Forging the action-token JWT with the realm HMAC key — couples to Keycloak internals.
4. Open self-registration and bind the first registrant with a LedgerForce setup token — needs a
   migration and a new auth flow, and lets anyone who reaches the IdP create accounts.
5. **(chosen)** The `setup` service creates the Owner's Keycloak account with a **unique random
   temporary password** and the required actions `CONFIGURE_TOTP` and `UPDATE_PASSWORD`, invites
   that subject as Owner in LedgerForce, and prints the tenant sign-in link with the one-time
   password once.

## Decision outcome

1. **First Owner** (`apps/worker/src/setup`): setup refuses to run unless the migrator URL logs in
   as `lf_migrator` and the app URL as `lf_app`, neither superuser nor BYPASSRLS. It applies the
   migrations and installs the queue as lf_migrator, then as lf_app under the new tenant's RLS
   creates the tenant (slug) and an `invited` Owner with `granted_by NULL` (provisioning) and two
   `system` audit rows. The Keycloak account gets a 25-character random password (`temporary`),
   so the first sign-in forces MFA enrolment and a new password; the one-time password stops
   working then (proven in SS-PLAT-23). Re-runs write nothing and print no password;
   `LF_SETUP_REISSUE=1` issues a new one only while the Owner is still `invited` (audited).
   The printed output is the "one-time owner setup link" of §6.3: `<public URL>/t/<slug>/auth/login`
   plus the one-time password.
2. **Realm** (`infra/compose/keycloak/ledgerforce-realm.json`): a two-level browser flow
   (password; OTP), `acr.loa.map = {urn:ledgerforce:loa:pwd: 1, urn:ledgerforce:loa:mfa: 2}` and
   client `default.acr.values = urn:ledgerforce:loa:mfa`, so **every login of this realm is MFA**
   and carries the `acr` that ADR-0025's default policy accepts, at first login and at step-up
   (HANDOVER question 13; RQ-0041 S11). No self-registration, no e-mail password reset, no direct
   grants, PKCE S256, brute-force protection, password policy length 12+.
3. **Admin access to Keycloak** is through the temporary bootstrap admin service account that
   Keycloak creates on its first start only; setup uses it. `/admin/` and `/realms/master/` are
   not routed publicly.
4. **Secrets** are compose file secrets generated by `init-secrets.sh` into a git-ignored folder,
   mounted only where needed (asserted by SS-PLAT-86); no secret is in an image, the compose file
   or an env file. Keycloak gets its own database and role; CONNECT is revoked from PUBLIC.
5. **One origin**: nginx serves the SPA, the API's prefixes and Keycloak's tenant realm; only it is
   published, on loopback by default, with TLS terminated in front of it in production.

## Consequences

### Good
- No default password; nothing new in the auth model; the Owner cannot reach LedgerForce without
  MFA; the HANDOVER Q13 mapping is configured and proven.

### Bad / risks
- The one-time password is a credential printed to the setup log (`docker compose logs setup`)
  until the Owner signs in. Mitigation: it is single use, the guide tells the operator to sign in
  promptly, and reissue invalidates the previous one. It has no time limit inside Keycloak.
- Realm-wide MFA is stricter than §6.2 (MFA for five roles): Approver and Viewer users also need
  an authenticator app.
- The bootstrap admin service account is temporary by Keycloak's design; it is not removed
  automatically (removal would block reissue); the operator guide covers rotating it.
- `nginx` keeps an explicit list of API prefixes until the API gets a prefix (RQ-0025 follow-up);
  a unit test keeps the list in step.

## Questions for the product owner

1. Accept "sign-in link + one-time password" as §6.3's one-time owner setup link, or require a
   true single-use link (SMTP or a Keycloak extension)?
2. Accept MFA for every self-hosted user, or limit it to the §6.2 roles (needs a per-user
   conditional flow)?
3. Keep the temporary bootstrap admin account after setup (needed for reissue), or remove it
   once the Owner has signed in?
